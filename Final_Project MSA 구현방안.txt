# 1. 에러 응답 구조 정의

(클라이언트 응답 및 내부 이벤트 모두 사용)

: 모든 에러 응답은 다음의 **표준화된 JSON 구조**를 따르도록 구현.

```java
// ex] common.response.ErrorResponse.java (공유 모듈에 위치)
import lombok.Builder;
import lombok.Getter;
import java.time.LocalDateTime;
import java.time.ZoneOffset;

@Getter
@Builder
public class ErrorResponse {
    private final String code;        // 에러 코드 (예: AUTH_FAILED, TODO_NOT_FOUND)
    private final String message;     // 사용자 친화적 메시지
    private final Object details;     // (선택 사항) 상세 정보 (예: 유효성 검사 오류 목록, 스택 트레이스)
    private final String timestamp;   // UTC 기준 에러 발생 시각 (ISO 8601)

    // 생성자 (필요에 따라 오버로딩)
    public ErrorResponse(String code, String message, Object details) {
        this.code = code;
        this.message = message;
        this.details = details;
        this.timestamp = LocalDateTime.now(ZoneOffset.UTC).toString();
    }
}
```

# 3. API 호출 에러 처리 (동기 통신)

: 클라이언트의 HTTP 요청에 대한 에러 처리는 기존 Spring Boot의 `@ControllerAdvice` 기반 `GlobalExceptionHandler`를 활용.

```java
// ex] common.error.GlobalExceptionHandler.java (각 서비스 또는 공유 모듈에 위치)
import common.error.ErrorCode; // ErrorCode 임포트
import common.response.ErrorResponse; // ErrorResponse 임포트
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.NoHandlerFoundException;

import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

@RestControllerAdvice
public class GlobalExceptionHandler {

    // 1. 커스텀 비즈니스 예외 처리
    @ExceptionHandler(CustomException.class)
    public ResponseEntity<ErrorResponse> handleCustomException(CustomException ex) {
        // 에러 로그는 별도의 로깅 시스템으로 (예: MDC 기반 Trace ID 포함)
        // logger.error("CustomException: {} - {}", ex.getErrorCode().getCode(), ex.getMessage(), ex);
        ErrorCode errorCode = ex.getErrorCode();
        return ResponseEntity
                .status(errorCode.getHttpStatus())
                .body(new ErrorResponse(errorCode.getCode(), errorCode.getMessage(), ex.getDetails())); // CustomException에 details 필드 추가 가능
    }

    // 2. @Valid 어노테이션 유효성 검사 실패 처리 (MethodArgumentNotValidException)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidationExceptions(MethodArgumentNotValidException ex) {
        List<Map<String, String>> errors = ex.getBindingResult().getFieldErrors().stream()
                .map(error -> {
                    Map<String, String> errorMap = new HashMap<>();
                    errorMap.put("field", error.getField());
                    errorMap.put("defaultMessage", error.getDefaultMessage());
                    errorMap.put("rejectedValue", String.valueOf(error.getRejectedValue()));
                    return errorMap;
                })
                .collect(Collectors.toList());

        ErrorCode errorCode = ErrorCode.COMMON_VALIDATION_FAILED;
        return ResponseEntity
                .status(errorCode.getHttpStatus())
                .body(new ErrorResponse(errorCode.getCode(), errorCode.getMessage(), errors));
    }

    // 3. JSON 파싱 오류, 잘못된 요청 바디 등 (HttpMessageNotReadableException)
    @ExceptionHandler(HttpMessageNotReadableException.class)
    public ResponseEntity<ErrorResponse> handleHttpMessageNotReadableException(HttpMessageNotReadableException ex) {
        // logger.error("HttpMessageNotReadableException: {}", ex.getMessage(), ex);
        ErrorCode errorCode = ErrorCode.COMMON_BAD_REQUEST;
        return ResponseEntity
                .status(errorCode.getHttpStatus())
                .body(new ErrorResponse(errorCode.getCode(), errorCode.getMessage(), "Request body is malformed or missing."));
    }

    // 4. 요청된 URI가 존재하지 않는 경우 (NoHandlerFoundException)
    //    application.properties: spring.mvc.throw-exception-if-no-handler-found=true, spring.resources.add-mappings=false
    @ExceptionHandler(NoHandlerFoundException.class)
    public ResponseEntity<ErrorResponse> handleNoHandlerFoundException(NoHandlerFoundException ex) {
        // logger.warn("NoHandlerFoundException: {}", ex.getMessage());
        ErrorCode errorCode = ErrorCode.COMMON_NOT_FOUND;
        return ResponseEntity
                .status(errorCode.getHttpStatus())
                .body(new ErrorResponse(errorCode.getCode(), errorCode.getMessage(), ex.getMessage()));
    }

    // 5. 그 외 예상치 못한 모든 예외 (최상위 예외 처리)
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleAllUncaughtException(Exception ex) {
        // **매우 중요**: 예측 불가능한 오류이므로 상세 로그 기록
        // logger.error("Unhandled exception occurred: {}", ex.getMessage(), ex);
        ErrorCode errorCode = ErrorCode.COMMON_INTERNAL_SERVER_ERROR;
        return ResponseEntity
                .status(errorCode.getHttpStatus())
                .body(new ErrorResponse(errorCode.getCode(), errorCode.getMessage(), null)); // Production에서는 details 제거 권장
    }
}
```

```java
// ex] common.error.CustomException.java (공유 모듈에 위치)
import lombok.Getter;

@Getter
public class CustomException extends RuntimeException {
    private final ErrorCode errorCode;
    private final Object details; // 추가적인 상세 정보를 담을 필드

    public CustomException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
        this.details = null;
    }

    public CustomException(ErrorCode errorCode, Object details) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
        this.details = details;
    }

    // 예외 발생 시 로그를 위한 생성자 (ex. logger.error("Error occurred", new CustomException(ErrorCode.XYZ, ex)))
    public CustomException(ErrorCode errorCode, Throwable cause) {
        super(errorCode.getMessage(), cause);
        this.errorCode = errorCode;
        this.details = cause != null ? cause.getMessage() : null;
    }
}
```

# 4. 이벤트 발행/소비 에러 처리 (비동기 통신)

: 이벤트 기반 통신에서는 HTTP 응답을 돌려줄 수 없으므로, **메시지 브로커(Kafka, RabbitMQ, Service_Bus[Azure] 등)의 기능을 적극 활용**하고 로깅 및 모니터링에 포커싱.

### **4.1. 이벤트 발행 시 에러 처리**

- **즉시 재시도 및 로컬 Outbox 패턴**: 이벤트 발행은 일반적으로 `KafkaTemplate.send()` 같은 비동기 메서드를 사용해서 발행 실패 시 브로커 재시도 로직을 기본적으로 활용하고, 핵심 비즈니스 이벤트는 **Outbox Pattern**을 적용해 견고함 상승.
    - **Outbox Pattern**: 이벤트 발행 시 DB 트랜잭션과 동일한 트랜잭션 내에서 **이벤트 레코드를 로컬 DB에 저장,** 이후 별도의 스케줄러(예: Spring Batch, Quartz)가 이벤트를 폴링하여 메시지 브로커에 발행, 성공적으로 발행되면 DB 레코드를 삭제, 발행 실패 시 재시도, 최종 실패 시 DLQ로 전송하거나 알림을 전송
- **에러 코드/메시지 활용**: API 호출에 대한 응답이라면 `EVENT_PUBLISH_FAILED` 등의 `ErrorCode`와 함께 `500 INTERNAL_SERVER_ERROR`를 반환.

### **4.2. 이벤트 소비 시 에러 처리**

메시지 리스너(`@KafkaListener`, `@RabbitListener`)에서 비즈니스 로직 처리 중 에러가 발생했을 때가 MSA에서 가장 중요한 부분임.

- **`ConsumerErrorHandler` 구현**:
Spring Kafka/AMQP는 리스너 컨테이너에 `ErrorHandler`를 등록하는 기능을 제공하며 이 핸들러에서 메시지 처리 실패 로직을 정의.

```java
// ex] common.event.KafkaConsumerErrorHandler.java (공유 모듈 또는 각 서비스에 위치)
import common.error.ErrorCode;
import common.error.CustomException;
import common.response.ErrorResponse;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.kafka.listener.ErrorHandler; // Spring Kafka ErrorHandler
import org.springframework.kafka.core.KafkaTemplate; // DLQ 전송용
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

// 스프링 카프카 2.7+ 부터는 DefaultErrorHandler 설정이 더 편리 (application.yml 참고)
// 이 클래스는 DefaultErrorHandler를 커스터마이징하거나, 그 이전 버전에서 직접 구현할 때 사용
@Component
public class KafkaConsumerErrorHandler implements ErrorHandler {

    private static final Logger log = LoggerFactory.getLogger(KafkaConsumerErrorHandler.class);
    private final KafkaTemplate<String, String> kafkaTemplate;
    private final ObjectMapper objectMapper;

    @Value("${app.kafka.dlq-topic-suffix:.DLT}")
    private String dlqTopicSuffix;

    public KafkaConsumerErrorHandler(KafkaTemplate<String, String> kafkaTemplate, ObjectMapper objectMapper) {
        this.kafkaTemplate = kafkaTemplate;
        this.objectMapper = objectMapper;
    }

    @Override
    public void handleError(Exception thrownException, ConsumerRecord<?, ?> consumerRecord) {
        String originalTopic = consumerRecord.topic();
        String recordKey = consumerRecord.key() != null ? consumerRecord.key().toString() : "null";
        String recordValue = consumerRecord.value() != null ? consumerRecord.value().toString() : "null";

        ErrorCode errorCode = ErrorCode.COMMON_MESSAGE_PROCESSING_FAILED; // 기본 에러 코드
        String errorMessage = thrownException.getMessage();
        Object details = null;

        // 예외 타입에 따른 ErrorCode 매핑
        if (thrownException.getCause() instanceof CustomException) {
            CustomException customEx = (CustomException) thrownException.getCause();
            errorCode = customEx.getErrorCode();
            errorMessage = customEx.getMessage();
            details = customEx.getDetails();
        } else if (thrownException instanceof MethodArgumentNotValidException) { // @Valid 실패 시 (이벤트 데이터 유효성)
            errorCode = ErrorCode.COMMON_VALIDATION_FAILED;
            errorMessage = "Event data validation failed.";
            details = ((MethodArgumentNotValidException) thrownException).getBindingResult().getFieldErrors().stream()
                    .map(error -> Map.of("field", error.getField(), "message", error.getDefaultMessage()))
                    .collect(Collectors.toList());
        }
        // 다른 특정 예외에 대한 ErrorCode 매핑 로직 추가

        // 1. 에러 상세 로깅 (Trace ID, Span ID 포함)
        log.error("Event processing failed on topic '{}'. Key: {}, Value: {}. ErrorCode: {}. Message: {}. Details: {}",
                  originalTopic, recordKey, recordValue, errorCode.getCode(), errorMessage, details, thrownException);

        // 2. 데드-레터 큐(DLQ)로 전송
        String dlqTopic = originalTopic + dlqTopicSuffix;
        try {
            // 원본 메시지와 함께 에러 메타데이터를 DLQ에 추가
            Map<String, Object> dlqPayload = new HashMap<>();
            dlqPayload.put("originalRecord", consumerRecord.value());
            dlqPayload.put("error", new ErrorResponse(errorCode.getCode(), errorMessage, details));
            dlqPayload.put("serviceName", "YOUR_SERVICE_NAME"); // 어떤 서비스에서 에러났는지 식별
            dlqPayload.put("timestamp", LocalDateTime.now(ZoneOffset.UTC).toString());
            dlqPayload.put("traceId", org.slf4j.MDC.get("traceId")); // OpenTelemetry/Sleuth 통합 시

            kafkaTemplate.send(dlqTopic, consumerRecord.key() != null ? consumerRecord.key().toString() : null, objectMapper.writeValueAsString(dlqPayload));
            log.info("Failed event sent to DLQ topic '{}'. Key: {}", dlqTopic, recordKey);
        } catch (Exception e) {
            log.error("Failed to send event to DLQ. Original topic: {}. DLQ topic: {}. Error: {}", originalTopic, dlqTopic, e.getMessage());
        }
        // 추가적으로 알림 시스템 연동 (Slack, PagerDuty 등)
    }

    @Override // ConsumerRecord가 아닌 Raw Data Exception을 처리할 때
    public void handleError(Exception thrownException, List<ConsumerRecord<?, ?>> records, Consumer<?, ?> consumer) {
        // 배치 처리 시 전체 메시지 목록에 대한 에러 처리
        records.forEach(record -> handleError(thrownException, record)); // 각 레코드별로 처리하도록 위임
    }
}
```

- **Kafka DLQ 설정 (application.yml)**

: 메시지 리스너가 특정 횟수 이상 실패할 경우 자동으로 DLQ로 메시지를 전송하도록 설정.

```yaml
# application.yml (각 서비스별로 설정) 예시
spring:
  kafka:
    consumer:
      group-id: your-consumer-group
      auto-offset-reset: latest
      enable-auto-commit: false # DLQ 사용 시 자동 커밋 비활성화 권장
    listener:
      ack-mode: MANUAL # DLQ 사용 시 수동 커밋 모드
      # DLQ를 위한 DefaultErrorHandler 설정 (Spring Boot 2.7+ 권장)
      common-configuration: defaultKafkaConsumerFactoryCustomizer
      default-error-handler:
        # DLQ 전송 설정: BackOff, DLQ Topic Resolver 설정
        # BackOff: 실패 시 재시도 간격 및 횟수 (예: 1초 간격으로 3번 재시도)
        fixed-retry:
          interval: 1000
          max-attempts: 3
        # DeadLetterPublishingRecoverer 설정: 실패한 메시지를 DLQ로 보냄
        dead-letter-publish-to: topic-name-resolver # 혹은 fixed-topic:<topic_name>
        # 토픽명 결정 로직 (원본 토픽 + .DLT)
        topic-name-resolver: beanName # 위 KafkaConsumerErrorHandler 빈 이름
        # 혹은 직접 클래스 지정: org.springframework.kafka.listener.DeadLetterPublishingRecoverer$SuffixAppendingDeadLetterPublishingRecoverer
        # suffix: .DLT
```

***주의*** : `default-error-handler` 설정은 Spring Boot 버전에 따라 다를 수 있어 공식 문서를 확인!

- **보상 트랜잭션 (Saga Pattern 등)**

: 이벤트 처리 중 치명적인 비즈니스 실패가 발생하여 분산 트랜잭션의 일부를 되돌려야 할 경우, **보상 이벤트를 발행** 하여 다른 서비스에 이미 완료된 작업을 롤백하도록 지시할 수 있음(또는 SAGA 패턴). 이는 복잡성이 높으므로 초기 단계부터 무리하게 도입하기보다는 필요에 따라 점진적으로 적용하는 것이 좋음.

# 5. 모니터링 및 로깅 전략 (MSA 필수)

### **5.1 구조화된 로깅**

: Logback, Log4j2 등을 사용하고, 각 서비스에서 모든 로그를 JSON 형식으로 출력하도록 설정. 이는 ELK Stack(Elasticsearch, Logstash, Kibana)이나 Grafana Loki 같은 중앙 집중식 로깅 시스템에서 쉽게 파싱하고 검색할 수 있도록 함.

### **5.2 Trace ID/Span ID 포함**

: Spring Cloud Sleuth (Spring Boot 3.x부터는 OpenTelemetry로 마이그레이션 권장)를 사용하여 모든 요청의 로그에 **Trace ID**와 **Span ID**를 자동으로 포함 시키기. 에러 발생 시 이 ID들을 통해 여러 서비스에 걸친 요청의 전체 흐름과 에러 발생 지점을 한눈에 파악할 수 있음.

### **5.3 서비스 명 포함**

: 각 서비스의 로그에 서비스 명을 명시하여 어떤 서비스에서 에러가 발생했는지 명확히 식별할 수 있도록.

### **5.4 알림 시스템 —> 이건 하지맙시다.**

: `5xx` 에러 발생, DLQ에 메시지가 적재될 때, 특정 `ErrorCode` (예: `COMMON_INTERNAL_SERVER_ERROR`, `TODO_AI_GENERATION_FAILED`) 발생 시 Slack, PagerDuty, 이메일 등으로 개발 팀에 자동으로 알림이 가도록 시스템을 구축.

### **5.5대시보드**

: Prometheus, Grafana 등을 활용해 서비스별 API 에러율, DLQ 적재량, 이벤트 처리 지연 시간 등을 실시간으로 모니터링하는 대시보드를 구축.

# 6. 에러 코드 관리 및 공유

### **6.1 공유 모듈**

: `ErrorCode` Enum, `ErrorResponse` DTO, `CustomException` 등 에러 처리와 관련된 모든 공통 클래스는 별도의 공유 모듈(Common Library)에 정의하고, 각 마이크로서비스가 이 모듈을 의존하도록 설정. 이는 모든 서비스가 동일한 에러 정책을 따르도록 강제하고 일관성을 유지하는 가장 효과적인 방법이다.

### **6.2 중앙 문서화**

: 정의된 모든 에러 코드, 사용자 메시지, 개발자 설명, HTTP 상태 코드 및 DLQ 처리 방안 등은 Notion, Confluence, Swagger 문서 등으로 중앙에서 상세하게 관리하고, 프론트엔드 / 백엔드 / 운영팀 (우리가..)이 항상 최신 정보를 확인할 수 있도록 공유.
